# Introduction to SIEM – TryHackMe Write-up

This repository contains my learning notes and write-up for the **Introduction to SIEM** room on TryHackMe. It covers the role of a Security Information and Event Management (SIEM) solution in a Security Operations Center (SOC), common log sources, log ingestion methods, and the alert investigation process.

## Overview

A **Security Information and Event Management (SIEM)** system is a core security solution used by SOC analysts to collect and analyse security events from different sources. By bringing logs together, standardising them, and correlating related events, a SIEM helps analysts identify potentially malicious activities.

## Learning Objectives

- Understand the different types of log sources.
- Identify the limitations of working with isolated logs.
- Recognise the importance of a SIEM solution.
- Explore common SIEM features.
- Understand log sources and how logs are ingested into a SIEM.
- Understand the alerting process and alert analysis.

## Topics Covered

### 1. Types of Log Sources

Log sources can broadly be grouped into two categories:

| Type | Description | Examples |
|---|---|---|
| **Host-centric** | Logs generated by individual hosts. | PCs, servers, and other endpoint systems. |
| **Network-centric** | Logs generated by host-to-host or host-to-internet communications. | Routers, firewalls, and network security devices such as IPS/IDS. |

### 2. Why SIEM Is Important

A SIEM brings information from multiple sources into one place and supports security monitoring through the following workflow:

1. **Collect** logs from various sources.
2. **Standardise / normalise** logs into a consistent format.
3. **Correlate** related events from different sources.
4. **Detect** potentially malicious activities using detection rules.

This helps SOC analysts investigate activity across systems instead of relying only on isolated logs.

### 3. Log Sources and Ingestion

#### Common log sources

**Windows machines**

- Windows events can be viewed using **Event Viewer**.

**Linux machines**

| Log location | Information recorded |
|---|---|
| `/var/log/httpd` | HTTP request, response, and error logs. |
| `/var/log/cron` | Events related to cron jobs. |
| `/var/log/auth.log` and `/var/log/secure` | Authentication-related logs. |
| `/var/log/kern` | Kernel-related events. |

#### Common log ingestion methods

- **Agent / Forwarder:** A lightweight agent is installed on an endpoint and configured to collect selected logs and send them to the SIEM server. Splunk uses a forwarder for this purpose.
- **Syslog:** A widely used protocol for collecting log data from systems such as web servers and databases and sending it to a central destination.
- **Manual upload:** Some SIEM solutions, including Splunk and ELK-based solutions, allow offline log data to be uploaded for analysis. The ingested data is then normalised and made available for analysis.
- **Port forwarding:** A SIEM can listen on a configured port while endpoints forward log data to that listening port.

### 4. Alerting Process and Detection Rules

SIEM detection rules identify events that match defined conditions and generate alerts for analysts to investigate.

#### Use case 1: Windows event logs cleared

Adversaries may attempt to clear event logs to remove evidence of their activity. The write-up identifies **Event ID 104** as an event associated with an attempt to clear event logs.

**Example detection logic:**

```text
IF Log Source = WinEventLog
AND EventID = 104
THEN Trigger Alert: Event Log Cleared
```

#### Use case 2: `whoami` command execution

The `whoami` command may be used after exploitation or privilege escalation to identify the current user context. Windows **Event ID 4688** can be used to monitor process creation.

Relevant fields:

- **Log Source:** Identifies the source that captured the event.
- **Event ID:** `4688`, associated with process creation.
- **NewProcessName:** The process name to check for `whoami`.

**Example detection logic:**

```text
IF Log Source = WinEventLog
AND EventCode = 4688
AND NewProcessName contains "whoami"
THEN Trigger Alert: WHOAMI Command Execution Detected
```

### 5. Alert Investigation and Response

When an alert is generated, analysts review the SIEM dashboard and examine the events or flows associated with the alert. They check which detection-rule conditions were met and decide whether the alert is a **true positive** or a **false positive**.

Possible follow-up actions include:

- **False positive:** Review and tune the detection rule to reduce similar false alerts.
- **True positive:** Continue with a deeper investigation.
- Contact the asset owner to understand the activity.
- If suspicious activity is confirmed, isolate the affected host.
- Block the suspicious IP address.

## Key Takeaways

- Logs from endpoints and network devices provide visibility into different parts of an environment.
- A SIEM centralises log collection, normalisation, correlation, and detection.
- Logs can be ingested using agents or forwarders, Syslog, manual uploads, and port forwarding.
- Detection rules use log fields and event conditions to identify suspicious behaviour.
- SIEM alerts require investigation to determine whether they are true or false positives and to decide on an appropriate response.
